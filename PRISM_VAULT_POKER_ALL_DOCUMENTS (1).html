Product statement

Prism Vault Poker is a polished, arcade-style video poker experience built for a limited promotion. It should feel as responsive and credible as a casino cabinet while remaining unmistakably a free entertainment product:

  • no purchase of coins;
  • no cash value;
  • no cash-out, withdrawal, gifting, or user-to-user transfer;
  • no outcome manipulation;
  • no real-money wagering;
  • no use of copyrighted card art in production without written permission.

The reference product image informs only the idea of collectible card art. The interface, name, colors, logo, controls, motion language, and promotional copy are intentionally original.

  • React Server Components for shell/data and client components for the game surface

  • Motion for React for orchestrated transitions; CSS transforms for the hot path
  • Supabase Auth, Postgres, Row Level Security, Storage, and Realtime where useful
  • Server-only PostgreSQL RPCs for wagering, dealing, drawing, and grants
  • Vercel for preview and production deployments
  • GitHub for source control, pull requests, branch protection, and CI
  • Vitest, Testing Library, Playwright, and a deterministic simulation runner

Architecture non-negotiables

  1. The browser never chooses an outcome, computes an authoritative payout, or writes a balance.
  2. Every balance change is an append-only ledger entry made in the same database transaction as the round or grant.
  3. A client-supplied idempotency key makes every balance-affecting request safe to retry.
  4. The canonical 52-card deck determines poker results. Collectible images are visual skins and never affect odds.
  5. Every round stores enough evidence to replay the deal, draw, evaluation, and payout.
  6. RLS is enabled on every table exposed through the Supabase API.
  7. Service-role and secret values are server-only.
  8. Fake coin language is visible near the balance and in every add-coin flow.
  9. Production card images come from owned/licensed storage, not unapproved hotlinks.
  10. Reduced-motion, keyboard, screen-reader, and muted-audio modes ship with the game.

MVP acceptance definition

A signed-in or anonymous promotional user can:

  • receive a 10,000 fake-coin starting balance;
  • add 10,000 free fake coins from the wallet drawer;
  • select 1, 3, 5, 10, or 25 hands;
  • activate 1, 2, or 3 visual tiers;
  • bet 1–5 coins per hand at a fake denomination of 1, 5, 10, or 25;
  • deal five cards, hold/unhold cards, draw, and receive server-calculated payouts;
  • see each tier and hand resolve independently;
  • inspect the paytable and transaction history;
  • play with keyboard, touch, mouse, reduced motion, and muted sound;
  • reload the page without losing a completed round or corrupting the balance.

Admins can activate/deactivate art, update display copy, schedule a promotion, adjust coin-grant limits, and publish a versioned paytable. Admins cannot edit settled round outcomes.

Suggested build order

  2. Database schema, RLS, ledger, and fake-coin grant
  3. Deterministic hand evaluator and simulation suite

  5. Single-hand game UI
  6. Multi-play and three-tier rendering
  7. Card-art ingestion and rotation
  8. Animation, audio, responsive polish, and accessibility
  9. Admin controls, analytics, security, and launch review

Vision

Create a short-session promotional game that combines the clarity of video poker, the spectacle of a multi-screen cabinet, and the delight of collectible card art. A new player should understand the core interaction within 30 seconds and feel a polished payoff within the first minute.

Working title: Prism Vault Poker
Tagline: Deal. Hold. Rise through the vault.

The working title is intentionally separate from Pokémon, the referenced packaging, and existing casino-machine brands.

Experience principles

  1. Instantly legible: deal, hold, draw, balance, bet, and payout are always visible.
  2. Visually deep, mechanically honest: tiers create spectacle; they do not secretly change odds.
  3. Collectible art, standard poker: art rotates independently from the canonical 52-card deck.
  4. Fast but not frantic: typical rounds resolve in 8–20 seconds.
  5. Free means free: fake coins can be replenished without purchase or advertising gates.
  6. Server authoritative: UI optimism never becomes balance authority.
  7. Original identity: no copied cabinet, logo, trade dress, or branded interface.

Users and roles

Role Capabilities
Guest Play with a device-scoped guest account, receive fake coins, view rules
Player Persist balance/history across devices, set preferences, join promotions
Support admin View user/round audit data and issue a reason-coded fake-coin grant
Content admin Manage promotions, art availability, messages, and paytable drafts
Super admin Publish versions and manage admin access; cannot rewrite settled rounds

Core modes

Quick Play

  • 1 tier
  • 1 or 3 hands
  • 5 coins per hand suggested
  • guided hold hints enabled by default

Multi-Play

  • 1, 3, 5, 10, or 25 hands
  • one shared first deal
  • held cards copied into each hand
  • each hand draws independently from a fresh remaining 47-card deck

Vault Stack

  • 1, 2, or 3 stacked visual tiers
  • each tier contains the selected hand count
  • all hands use the same published paytable
  • every tier is paid for, dealt, evaluated, and settled independently
  • tier count multiplies stake and variance, not return percentage

Showcase / Demo

  • fixed fake balance
  • scripted tutorial rounds clearly labeled “DEMO”
  • outcomes never enter real promotional leaderboards
  • useful for events, kiosks, and sales demonstrations

Functional requirements

Account and session

  • Support anonymous session creation with optional email upgrade.
  • Resume an unresolved server round after refresh.
  • Persist audio, motion, help, denomination, hands, and tier preferences.
  • Display session timeout and reconnect states without discarding settled data.

Game configuration

  • Denomination: 1, 5, 10, or 25 fake credits.
  • Coins per hand: 1–5.
  • Hands per tier: 1, 3, 5, 10, or 25.
  • Active tiers: 1–3.
  • Show total wager before Deal.
  • Disable Deal if the balance is too low and open the free add-coins drawer.

Round

  • Deal five canonical cards.
  • Open any visible card in a centered detail viewer with a larger image and available card stats.
  • Hold/unhold before Draw only through a distinct Hold control so viewing never changes the hand.
  • Copy each tier’s holds to every active hand within that tier.
  • Resolve all hands server-side.
  • Animate outcomes in a deterministic order that never changes amounts.
  • Show total win, per-tier win, and individual hand classifications.
  • Credit the full payout atomically before the win animation finishes.

Fake coins

  • New player grant: 10,000.
  • Manual “Add 10,000 Fake Coins” action.
  • Optional daily grant: 5,000.
  • Visible “No cash value” label.
  • Full ledger history with reason and round reference.
  • No purchase, withdrawal, transfer, gifting, or redemption.

Content and admin

  • Versioned paytables and game configuration.
  • Draft/publish workflow for promotions.
  • Art manifest import with licensing status.
  • Maintenance banner and kill switch.
  • Read-only round explorer and wallet ledger.
  • Reason-coded admin grants with limits and audit logs.

MVP

  • One 9/6 Jacks or Better paytable
  • Three visual tiers
  • Up to 25 hands per tier
  • Fake wallet and grants
  • Guest and email auth
  • 295-card source manifest plus licensed-storage pipeline
  • Responsive desktop/tablet/mobile UI
  • Essential motion/audio and accessibility
  • Admin read views and configuration publishing
  • Automated unit, integration, end-to-end, and statistical tests

Later phases

  • Daily missions with cosmetic rewards
  • Collection gallery showing art encountered
  • Non-monetary achievements
  • Promotional leaderboard based on normalized hand score, not purchased/granted balance
  • Theme packs made only from cleared assets
  • Installable PWA and kiosk mode
  • Localization

Explicitly out of scope

  • Real-money deposits or purchases
  • Crypto, tokens, NFTs, or cash-equivalent prizes
  • Cash-out, redemption, or user-to-user transfers
  • Sportsbook, slots, roulette, or other wagering products
  • Dynamic odds by user, balance, history, or marketing segment
  • Client-side outcome generation
  • Scraping or republishing card images without rights
  • Use of Pokémon, Nintendo, or existing casino-machine names in the product brand

Round completion At least 85% of dealt rounds reach Draw
Deal API p95 Under 500 ms excluding cold start
Draw API p95 Under 700 ms excluding animation
Input responsiveness Under 100 ms local response
Game-surface frame rate 60 fps target on supported devices
Balance reconciliation 100%
Duplicate settlement 0
WCAG 2.2 AA for primary flows

Primary user stories

  • As a first-time player, I can understand fake coins and play without registering.
  • As a player, I can clearly see the cost before I deal.
  • As a player, I can hold one card once and have that choice apply to every hand in that tier.
  • As a player, I can click a card to inspect its full image and stats without changing my hold.
  • As a player, I can tell exactly why I won and how the total was calculated.
  • As a player with a low balance, I can add fake coins for free.
  • As a returning player, I can resume after a refresh.
  • As an admin, I can inspect but not rewrite a settled round.
  • As a compliance reviewer, I can verify that fake coins cannot be bought or redeemed.

Brand and Visual System

Original direction

Prism Vault Poker should feel like a futuristic gallery vault, not a Pokémon product and not a copy of a particular video-poker cabinet.

Visual keywords:

  • obsidian glass;
  • refracted light;
  • precision metal;
  • ultraviolet energy;
  • museum-grade card presentation;
  • quiet confidence;
  • sharp, tactile controls.

Avoid:

  • teal/yellow/magenta combinations from the supplied package;
  • circular capture-device motifs;
  • monster-ball icons;
  • lightning-bolt logos;
  • copied Pokémon fonts, shapes, terminology, or sound cues;
  • copied cabinet chrome, button arrangements, or branded paytable treatments.

Identity

Logo concept

An abstract open vault made from three offset rhombi. The negative space forms a subtle “V.” It must remain geometric and non-character-based.

Voice

  • Short: “Deal,” “Hold,” “Draw,” “25 hands”
  • Transparent: “150 fake coins total”
  • Energetic without pressure: “Vault cleared”
  • Never: “real bet,” “cash,” “buy coins,” “deposit,” “wager real money,” or urgency designed to induce spending

Color tokens

Token Value Use
--pv-ink-950 #07080D page background
--pv-ink-900 #0D1019 machine shell
--pv-ink-800 #151A28 panels
--pv-violet-500 #8057FF primary energy/accent
--pv-blue-400 #55A7FF secondary accent
--pv-ice-300 #AEEBFF selected/held states
--pv-coral-400 #FF6F91 bonus emphasis
--pv-gold-400 #F2BC61 wins and coin value
--pv-mint-400 #53D6B4 success
--pv-red-400 #FF657A destructive/error
--pv-white #F7F9FF primary text
--pv-slate-300 #AAB3C7 secondary text

Use violet, blue, and ice as the main signature. Gold appears only for payouts and the fake-coin balance.

Typography

  • Display: Space Grotesk, 600–700
  • UI/body: Inter, 400–700
  • Numeric/paytable: JetBrains Mono, 500–700 with tabular numerals
  • Minimum body size: 16 px
  • Balance and total win: tabular numerals to prevent layout shift

If external font loading is undesirable, use carefully tuned system fallbacks.

Game Rules and Multi-Tier Flow

Original file: 04_GAME_RULES_AND_MULTI_TIER_FLOW.md · SHA-256: efc7f9c68b406d1f58702226e31bcc889e5b95b04dc8317c9fab96bdcdb21a75

Canonical game

The MVP is conventional Jacks or Better draw poker:

  1. A canonical 52-card deck contains four suits and ranks 2 through Ace.
  2. The server shuffles and deals five cards.
  3. The player holds zero to five positions.
  4. On Draw, held positions remain.
  5. Every active hand receives replacement cards from its own independently shuffled remaining 47-card deck.
  6. Each final five-card hand is classified.
  7. Payout equals the published paytable amount multiplied by fake denomination.

No jokers or wild cards in the MVP.

Art is not game state

Each canonical card has:

  • canonical_card_id such as AS or 10H;
  • rank;
  • suit;
  • asset_id selected from the licensed art rotation;
  • a visible rank/suit overlay.

The poker evaluator reads only canonical rank and suit. Art rarity, character, type, market value, filename, or URL must never affect the shuffle, hand class, or payout.

Opening a card’s detail viewer is a presentation event only. It does not alter the hold mask, RNG state, draw order, round deadline, stake, or payout.

Multi-play

Available hand counts: 1, 3, 5, 10, and 25 per tier.

The initial five-card deal is shared within a tier so the player makes one hold decision. At Draw:

  • held positions are copied to every hand in that tier;
  • each hand starts with the same original 52-card deck;
  • the original five dealt cards are removed;
  • each hand independently shuffles the remaining 47 cards;
  • each hand draws the required number of replacements.

This matches familiar multi-hand video-poker behavior and prevents one hand’s draw from consuming another hand’s cards.

Multi-tier

Available tier counts: 1, 2, or 3.

Tiers are independent paid play groups presented as a vertical stack:

  • each tier receives its own initial five-card deal;
  • the player sets holds for each tier before Draw;
  • each tier contains the selected number of hands;
  • every hand uses the same paytable;
  • tier count multiplies total hands, stake, wins, and variance;
  • tier labels do not create hidden multipliers.

For a faster optional mode, linked_holds=true may copy the Tier 1 hold mask to Tier 2 and Tier 3. The UI must clearly show this setting. Default is false, letting the player make the best choice for each tier.

Cost formula

total_fake_coin_cost =
  denomination
  × coins_per_hand
  × hands_per_tier
  × active_tiers

Example:

denomination = 5
coins_per_hand = 5
hands_per_tier = 10
active_tiers = 3

total cost = 5 × 5 × 10 × 3 = 750 fake coins

The exact total appears immediately above the Deal button.

Round state machine

stateDiagram-v2
    [*] --> Ready
    Ready --> Dealt: start_round
    Dealt --> Dealt: update local holds
    Dealt --> Settled: draw_round
    Settled --> Complete: reveal finished
    Complete --> Ready: new configuration
    Dealt --> Expired: hold deadline exceeded
    Expired --> Settled: server auto-stands

Expired uses “stand” behavior: all originally dealt cards are held and the round is evaluated. It does not silently refund or reroll.

  • round id;
  • user id;
  • promotion id;
  • paytable version;
  • RNG version;
  • art-manifest version;
  • denomination;
  • coins per hand;
  • hands per tier;
  • active tiers;
  • total stake;
  • state;
  • client idempotency keys;
  • created/dealt/settled timestamps;
  • initial canonical cards by tier;

Fairness objective

Every legal five-card combination must have the expected probability under a standard 52-card deck. No user attribute, balance, art selection, promotion segment, or past result may alter the shuffle.

The client is never trusted for:

  • random numbers;
  • card order;
  • hand classification;
  • payout;
  • balance;
  • timing-based entropy.

RNG versioning

Every round stores rng_version. Changing any of the following requires a new version and a new simulation report:

  • random-byte source;
  • bounded-integer method;
  • shuffle implementation;
  • deck representation;
  • multi-hand derivation;
  • hold-mask handling;
  • evaluator;
  • paytable.

Random source

Use a cryptographically secure server-side source:

  • PostgreSQL pgcrypto random bytes inside the authoritative RPC; or
  • Web Crypto in a trusted server/Edge context, with the resulting order persisted before returning.

The preferred MVP design keeps wallet locking, shuffle, round persistence, and debit in one PostgreSQL transaction.

Do not use:

  • Math.random();
  • timestamps as seeds;
  • incremental round ids;
  • user ids;
  • browser entropy;
  • predictable pseudo-random generators in production.

Unbiased bounded integers

Modulo can introduce bias when the random integer range is not divisible by the target range. Use rejection sampling:

function secureInt(maxExclusive):
  require maxExclusive > 0
  limit = floor(2^32 / maxExclusive) * maxExclusive
  do:
    x = uint32(secureRandomBytes(4))
  while x >= limit
  return x mod maxExclusive

Fisher–Yates shuffle

function shuffle(deck):
  result = copy(deck)
  for i from result.length - 1 down to 1:
    j = secureInt(i + 1)
    swap result[i], result[j]
  return result

Do not sort with a random comparator.

Canonical deck

Use compact integer ids 0..51:

rankIndex = cardId mod 13       // 0=2 ... 8=10, 9=J, 10=Q, 11=K, 12=A
suitIndex = floor(cardId / 13) // 0..3

Persist canonical ids, not just display labels.

Tier and hand generation

At Deal:

  • generate one independent shuffled deck per active tier;
  • store the first five cards as that tier’s initial hand;
  • store a commitment or encrypted order for the remaining deck evidence.

At Draw for each hand in a tier:

  • begin with canonical cards not present in the initial five;
  • create an independent shuffle using fresh secure randomness;
  • fill only unheld positions;
  • store the final cards and sufficient audit evidence.

Do not derive one hand by slicing a single remaining deck across all hands. Standard multi-hand play requires independent replacement draws.

Art mapping

After canonical cards exist, assign art skins through a separate deterministic mapping:

offset = hash(roundId + ":" + tierIndex + ":" + handIndex) mod 295
step = 7 // coprime with 295
assetIndex(position) = (offset + canonicalCardId * step) mod 295

Store the actual asset_id used. If an asset is disabled, advance through the active manifest without changing the canonical card.

Art mapping may be computed after settlement because it cannot affect game math. A manifest/version mismatch must never trigger a redeal.

  if groups == [3,2]: FULL_HOUSE
  if isFlush: FLUSH
  if isStraight: STRAIGHT
  if groups == [3,1,1]: THREE_OF_A_KIND
  if groups == [2,2,1]: TWO_PAIR
  if groups == [2,1,1,1] and pair rank >= J: JACKS_OR_BETTER
  return NO_WIN

- random-byte source;
- bounded-integer method;
- shuffle implementation;
- deck representation;
- multi-hand derivation;
- hold-mask handling;
- evaluator;
- paytable.

## Random source

Use a cryptographically secure server-side source:

- PostgreSQL `pgcrypto` random bytes inside the authoritative RPC; or
- Web Crypto in a trusted server/Edge context, with the resulting order persisted before returning.

The preferred MVP design keeps wallet locking, shuffle, round persistence, and debit in one PostgreSQL transaction.

Do not use:

- `Math.random()`;
- timestamps as seeds;
- incremental round ids;
- user ids;
- browser entropy;
- predictable pseudo-random generators in production.

## Unbiased bounded integers

Modulo can introduce bias when the random integer range is not divisible by the target range. Use rejection sampling:

```text
function secureInt(maxExclusive):
  require maxExclusive > 0
  limit = floor(2^32 / maxExclusive) * maxExclusive
  do:
    x = uint32(secureRandomBytes(4))
  while x >= limit
  return x mod maxExclusive
```

## Fisher–Yates shuffle

```text
function shuffle(deck):
  result = copy(deck)
  for i from result.length - 1 down to 1:
    j = secureInt(i + 1)
    swap result[i], result[j]
  return result
```

Do not sort with a random comparator.

## Canonical deck

Use compact integer ids `0..51`:

```text
rankIndex = cardId mod 13       // 0=2 ... 8=10, 9=J, 10=Q, 11=K, 12=A
suitIndex = floor(cardId / 13) // 0..3
```

Persist canonical ids, not just display labels.

## Tier and hand generation

At Deal:

- generate one independent shuffled deck per active tier;
- store the first five cards as that tier’s initial hand;
- store a commitment or encrypted order for the remaining deck evidence.

At Draw for each hand in a tier:

- begin with canonical cards not present in the initial five;
- create an independent shuffle using fresh secure randomness;
- fill only unheld positions;
- store the final cards and sufficient audit evidence.

Do not derive one hand by slicing a single remaining deck across all hands. Standard multi-hand play requires independent replacement draws.

## Art mapping

After canonical cards exist, assign art skins through a separate deterministic mapping:

```text
offset = hash(roundId + ":" + tierIndex + ":" + handIndex) mod 295
step = 7 // coprime with 295
assetIndex(position) = (offset + canonicalCardId * step) mod 295
```

Store the actual `asset_id` used. If an asset is disabled, advance through the active manifest without changing the canonical card.

Art mapping may be computed after settlement because it cannot affect game math. A manifest/version mismatch must never trigger a redeal.

## Evaluator pseudocode

```text
function evaluate(cards):
  ranks = countsByRank(cards)
  suits = countsBySuit(cards)
  isFlush = any suit count == 5
  distinct = sorted distinct rank values
  isWheel = distinct == [A,2,3,4,5]
  isStraight = five consecutive ranks or isWheel
  groups = rank counts sorted descending

  if isFlush and ranks are [10,J,Q,K,A]: ROYAL_FLUSH
  if isFlush and isStraight: STRAIGHT_FLUSH
  if groups == [4,1]: FOUR_OF_A_KIND
  if groups == [3,2]: FULL_HOUSE
  if isFlush: FLUSH
  if isStraight: STRAIGHT
  if groups == [3,1,1]: THREE_OF_A_KIND
  if groups == [2,2,1]: TWO_PAIR
  if groups == [2,1,1,1] and pair rank >= J: JACKS_OR_BETTER
  return NO_WIN
```

## Statistical simulation

Before publishing a paytable:

1. Unit-test every category and edge case.
2. Exhaustively classify all 2,598,960 five-card combinations.
3. Compare counts to the reference table.
4. Run at least 100 million deterministic strategy rounds for expected return analysis.
5. Report seed, code commit, RNG version, paytable version, sample size, RTP, category frequencies, confidence intervals, and failures.
6. Repeat on CI for a smaller smoke sample; run the full simulation in a scheduled or release workflow.

## Optimal-play return

The 9/6 Jacks or Better schedule is often cited near 99.54% with optimal strategy. That value depends on:

- correct max-coin Royal behavior;
- correct hand evaluator;
- correct replacement model;
- exact optimal hold decisions;
- no extra side awards or fees.

Do not display a return figure until an independent reviewer reproduces it from the shipped commit.

## Commit/reveal option

For stronger player-facing auditability:

1. Before Deal, generate a server secret.
2. Return `commitment = SHA-256(secret + canonical deck orders + round id)`.
3. Settle and persist the round.
4. Reveal the secret and serialized orders after settlement.
5. Provide a verifier page.

Commit/reveal proves the stored order was not changed after commitment. It does not by itself prove that the secret was uniformly random, so retain statistical and implementation audits.

## Fairness controls

- Immutable settled rounds.
- Database constraints on legal cards and states.
- Versioned, reviewed evaluator.
- Server-only secret material.
- Audit log for paytable/config publication.
- Automated distribution monitoring.
- Alert if category frequencies exceed control limits.
- Never “tighten,” “loosen,” or personalize outcomes.

Motion principles

  • Motion explains state.
  • Results are settled before celebration begins.
  • The player can skip reveal animation.
  • The card viewer pauses decorative background motion.
  • Nothing essential depends on sound, vibration, or color.
  • Reduced-motion mode is complete, not an afterthought.

Timing tokens

Token Duration Use
instant 80 ms press feedback
fast 140 ms toggles, focus surfaces
normal 220 ms drawers, card hold
deliberate 360 ms deal/replace card
hero 600 ms major win/tier transition

Easing:

  • enter: cubic-bezier(.16,1,.3,1);
  • exit: cubic-bezier(.7,0,.84,0);
  • physical settle: spring with low bounce;
  • no perpetual movement on controls.

Deal choreography

  1. Deal request enters pending state; CTA compresses and label becomes “Securing deal…”.
  2. On confirmed response, fake balance changes immediately in the data model.
  3. Tier shell edge lights from Tier 1 upward.
  4. Five cards enter with 55 ms stagger inside each tier.
  5. Between tiers use 110 ms offset.
  6. Card arrives with translate/scale and a short face reveal.
  7. Hold controls fade in after the last primary card.

At 25 hands, animate only the primary hand in full. Compact hands appear in grouped waves to protect frame rate.

Hold choreography

The Hold button:

  • depresses 2 px;
  • adds ice outline and lock icon;
  • displays “HELD” in text;
  • copies the marker to corresponding positions in additional hands;
  • uses a 140–180 ms transition.

Opening the card viewer never triggers hold motion.

Draw choreography

  1. Held cards remain anchored.
  2. Unheld cards dip and fade.
  3. Returned final cards rise with a short flip or crossfade.
  4. Tier 1 resolves first, then Tier 2, then Tier 3.
  5. Winning hands receive classification chips.
  6. Total payout count-up starts only after the first visible result.
  7. Balance already reflects the confirmed server amount.

“Reveal all” jumps to complete visual state in under 150 ms.

Win intensity

Level Example Treatment
0 No Win quiet classification; no shake
1 Pair/Two Pair gold edge and small coin tick
2 Trips/Straight/Flush tier sweep and short particle ribbon
3 Full House/Four Kind shell pulse and richer sound
4 Straight/Royal Flush full vault aperture, controlled particles, prominent result

Do not flash faster than accessibility thresholds. Avoid full-screen white flashes.

Fake-coin feedback

Stake

  • balance number rolls/crossfades to confirmed post-stake amount;
  • a small −750 label travels toward the tier stack;
  • screen reader announces once.

Payout

  • result strip shows exact total immediately;
  • optional count-up takes 400–1,200 ms based on magnitude;
  • coin particles are capped and pooled;
  • pressing/clicking skips count-up;
  • screen reader announces final amount, never intermediate numbers.

Add fake coins

  • drawer closes only after server confirmation;
  • +10,000 rises from the balance;
  • 12–20 restrained prism coins arc toward the meter;
  • no slot-reel sound or purchase cue.

Centered card-viewer motion

Open:

  • backdrop fades to 70% dark in 180 ms;
  • selected card uses a shared-layout transition toward center when performance permits;
  • dialog settles at scale 0.98 → 1;
  • stats fade in after the image starts loading.

Close:

  • reverse toward the triggering card when it remains mounted;
  • otherwise fade/scale out;
  • restore background state and focus.

Previous/Next:

  • current image slides 5% and fades;
  • next image enters from the opposite side;
  • stats crossfade with stable panel dimensions;
  • preloaded adjacent image prevents a white flash.

Zoom:

  • transform only the image inside a clipped viewer;
  • no layout expansion;
  • pan bounds prevent losing the card entirely;
  • Reset button always available.

Reduced motion:

  • no shared-layout travel, flip, parallax, or slide;
  • use 100 ms opacity changes;
  • viewer and results appear immediately.

Holographic treatment

Add an original, subtle prism sheen over approved card art:

  • CSS pseudo-element;
  • pointer-position input capped at 10–12° perceived tilt;
  • disabled for compact grids, touch scroll, reduced motion, and low-power mode;
  • never alter or obscure card text;
  • decorative and aria-hidden.

Do not imitate a particular physical foil pattern owned by the source brand.

Audio design

Original sound palette:

  • soft metal contact for Deal;
  • glassy latch for Hold;
  • layered crystalline tones for tiers;
  • warm coin tick for payout;
  • short vault chord for major win.

Requirements:

  • muted until user interaction where browser policy requires;
  • persistent mute and volume;
  • separate music/effects only if music exists;
  • audio sprites/preloaded buffers;
  • no copied franchise or casino-machine sounds;
  • no voice line that pressures continued play.

Haptics

Where supported:

  • short tap on Hold;
  • double short tap on meaningful win;
  • no vibration storm for multi-hand results;
  • preference toggle;
  • disabled when reduced motion is requested.

Performance

  • animate transform and opacity;
  • avoid layout reads inside animation loops;
  • pool particles;
  • virtualize compact hands;
  • pause offscreen tier animation;
  • use will-change briefly, then release it;
  • test three tiers × 25 hands on target mobile hardware;
  • high-resolution viewer image loads on demand.

- next image enters from the opposite side;
- stats crossfade with stable panel dimensions;
- preloaded adjacent image prevents a white flash.

Zoom:

- transform only the image inside a clipped viewer;
- no layout expansion;
- pan bounds prevent losing the card entirely;
- Reset button always available.

Reduced motion:

- no shared-layout travel, flip, parallax, or slide;
- use 100 ms opacity changes;
- viewer and results appear immediately.

## Holographic treatment

Add an original, subtle prism sheen over approved card art:

- CSS pseudo-element;
- pointer-position input capped at 10–12° perceived tilt;
- disabled for compact grids, touch scroll, reduced motion, and low-power mode;
- never alter or obscure card text;
- decorative and `aria-hidden`.

Do not imitate a particular physical foil pattern owned by the source brand.

Original sound palette:

- soft metal contact for Deal;
- glassy latch for Hold;
- layered crystalline tones for tiers;
- warm coin tick for payout;
- short vault chord for major win.

Requirements:

- muted until user interaction where browser policy requires;
- persistent mute and volume;
- separate music/effects only if music exists;
- audio sprites/preloaded buffers;
- no copied franchise or casino-machine sounds;
- no voice line that pressures continued play.

## Haptics

Where supported:

- short tap on Hold;
- double short tap on meaningful win;
- no vibration storm for multi-hand results;
- preference toggle;
- disabled when reduced motion is requested.

- animate `transform` and `opacity`;
- avoid layout reads inside animation loops;
- pool particles;
- virtualize compact hands;
- pause offscreen tier animation;
- use `will-change` briefly, then release it;
- test three tiers × 25 hands on target mobile hardware;
